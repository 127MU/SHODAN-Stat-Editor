# r4.2 发布后的诊断复查

日期：2026-11-08。本文件记录后续源码修复，不表示已替换 GitHub 上的 r4.2 安装包。

## 破坏参数安装失败

诊断中的两次安装在封装阶段返回：

```text
generated_destruction_settings.dl_bin：不支持的数据块对齐：0xf65
```

同一日志中的较早两次安装和一次恢复成功，不能把后面的失败归因于整体路径权限或网络。失败请求尚未进入创建备份、写入文件阶段。

原封装器对所有块头强制要求 4 字节对齐，但 LDLD 的变长载荷会使后续块头处于其他偏移。这不是数据损坏的充分依据。修复后只要求被选作哈希求解锚点的块满足现有算法的对齐约束，其他块继续严格检查边界和标记。

校正仍限于块头已有保留字节和明确授权的浮点字段。输出长度、目标 Murmur 哈希、密封后回读和非授权区域逐字节校验保持不变。

`tests/test_native_destruction_correction.py` 使用本地固定原始数据复现：1,647 个块、1,312 个非 4 字节对齐块，修改私有副本并导出回读。测试不写游戏目录。

## 4.5.1 预设

已对照仓库 `v4.5.1` 的 `offline/desktop_features.lua`：该版本文本容器同样使用 `SHODAN-PRESET 1`，不需要仅因版本号而拒绝。

本轮兼容与保护：

- 接受 Windows UTF-8 BOM 和容器首尾空白，包括旧配置式正文导入入口。
- 本地 `preset_01.txt` 等旧存档扫描也识别完整文本容器，不能仅因文件带 `SHODAN-PRESET 1` 头就静默忽略；正文和容器共用导入判定。
- 已有确定映射的字段继续解析；需要专用处理、当前无法定位的字段保留在原预设中并提示跳过。
- 导入和读取的返回消息带出兼容警告，避免仅显示成功而隐藏丢失的字段。
- 数值全部无法定位且没有其他可应用内容时，停止读取，避免替换当前待写入修改。
- 对有歧义的字段、共享字段矛盾值、无效枚举和类型不匹配仍拒绝猜测。

诊断日志没有记录预设读取失败请求。用户已确认来源为 4.5.1，但尚没有具体预设文本或原始错误，因此不能把上述兼容修复等同于已验证该份预设的所有字段。

## 修复后护甲再次写入

自动修复将护甲数值文件恢复为安装前状态并清理旧登记时，原有护甲配置可能仍被视为“已经安装”。现在将重新应用标记与修复事务一起保存，预览明确列出待重新应用项。成功写入后才清除标记。重启程序不能丢失这个状态。

隔离测试分别覆盖文件被外部精确还原、文件被删除两种情况，检查修复、重启、写入后的完整明文一致性，再恢复隔离副本。

## 本地旧数据不能拖垮参数列表

无法解析的 `draft.json` 或 `configuration.json` 原先会使整个 `game-open` 失败，界面因此没有参数可列出。现在先打开当前游戏数据，独立报告本地配置错误。原文件在启动时保持不变；修复前阻止编辑保存和安装，避免覆盖尚未恢复的旧数据。

自动修复会将可读取且大小受限的无效本地文件事务化完整备份为带内容哈希的恢复副本，再重新加载当前数据。权限错误、超大文件、恢复副本不一致仍明确报错，不能假装恢复了其不可解析的参数。原本能解析但与当前游戏指纹不匹配的字节草稿继续使用既有冲突恢复副本流程，绝不把旧偏移直接套入新版数据。
